# AlphaLens AI: Technical Decisions & Architecture Justification

This document outlines the core technical decisions made for AlphaLens AI. Every choice was deliberately evaluated against the constraint of a 7-day internship project, prioritizing speed of delivery, reliability, and modular architecture over enterprise-scale complexity.

---

## 1. Frontend: React.js vs Next.js

1. **Why it was selected:** React.js provides a robust, component-based architecture that is easy to spin up using Vite. It allows for a strictly separated frontend layer.
2. **Why alternatives were not selected:** Next.js is powerful, but it blends frontend and backend logic. For a project heavily reliant on complex backend orchestration (LangGraph), strict separation of concerns is safer for a 7-day sprint.
3. **Benefits for this project:** Rapid development, huge ecosystem of community support, and extremely simple deployment for static assets.
4. **Trade-offs accepted:** No out-of-the-box Server-Side Rendering (SSR) or SEO optimization.
5. **Future upgrade possibilities:** Migrating to Next.js if SEO becomes a requirement or if the app needs complex server-side data fetching.

## 2. Backend: Express.js vs Next.js API Routes

1. **Why it was selected:** Node.js with Express is the industry standard for lightweight, standalone backend servers.
2. **Why alternatives were not selected:** Next.js API routes have strict timeout limits on serverless deployments (e.g., Vercel's 10-50 second limits). AI workflows often take longer than 60 seconds. A dedicated Express server allows for long-running processes and easy WebSockets/Server-Sent Events (SSE) implementation.
3. **Benefits for this project:** Total control over API execution time, streaming, and server environment.
4. **Trade-offs accepted:** Requires managing a separate deployment pipeline from the frontend.
5. **Future upgrade possibilities:** Refactoring into microservices (e.g., separating the API Gateway from the LangGraph worker) if scale demands it.

## 3. Database: MongoDB vs PostgreSQL

1. **Why it was selected:** MongoDB is a NoSQL document database. Its JSON-like structure maps perfectly to the unstructured Markdown/JSON outputs generated by LLMs.
2. **Why alternatives were not selected:** PostgreSQL requires designing and migrating strict relational schemas. We don't have complex relational entities (like users, orders, and payments); we just need to cache JSON reports by ticker symbol.
3. **Benefits for this project:** Zero schema friction. We can dump the entire LangGraph output directly into a document and retrieve it instantly.
4. **Trade-offs accepted:** Lack of ACID compliance across complex transactions (which we don't need).
5. **Future upgrade possibilities:** Moving to PostgreSQL if user accounts, billing, and complex relationship mapping become necessary.

## 4. AI Orchestration: LangGraph vs Single Prompt

1. **Why it was selected:** LangGraph enables stateful, multi-actor applications. It allows us to define distinct agents (Data, News, Analyst, Risk) that can communicate and iterate.
2. **Why alternatives were not selected:** A massive "Single Prompt" to an LLM (asking it to do everything at once) results in severe hallucinations, skipped instructions, and generic outputs. 
3. **Benefits for this project:** Separation of concerns. The Data Agent only cares about numbers; the Risk Agent only cares about downsides. This dramatically increases the quality and reliability of the final report.
4. **Trade-offs accepted:** Much higher backend complexity and slightly slower total execution time as agents pass state back and forth.
5. **Future upgrade possibilities:** Adding a "Human-in-the-loop" node where the LangGraph pauses and asks the user for clarification on ambiguous data before continuing.

## 5. LLM Provider: Gemini vs OpenAI

1. **Why it was selected:** Google Gemini offers an incredibly fast inference speed, a generous free tier, and massive context windows (useful for passing in dozens of news articles).
2. **Why alternatives were not selected:** OpenAI's API is excellent but strictly pay-as-you-go, which can accrue unexpected costs during high-volume testing in a 7-day sprint.
3. **Benefits for this project:** Zero cost for development, fast responses, and excellent JSON formatting capabilities.
4. **Trade-offs accepted:** OpenAI's GPT-4o slightly edges out competitors in deep reasoning, but Gemini is more than capable for this MVP's synthesis tasks.
5. **Future upgrade possibilities:** Building an LLM-agnostic wrapper so the user can select their preferred model (Gemini, Claude, or GPT) via the UI.

## 6. Styling: Tailwind CSS vs Material UI

1. **Why it was selected:** Tailwind CSS is a utility-first framework that allows for rapid, custom UI development directly within JSX.
2. **Why alternatives were not selected:** Material UI (MUI) looks very "enterprise" out-of-the-box and is difficult to customize deeply. We want a modern, bespoke, AI-native aesthetic.
3. **Benefits for this project:** No context switching between CSS files and JSX; highly responsive design is achieved quickly.
4. **Trade-offs accepted:** JSX files can become cluttered with long class strings.
5. **Future upgrade possibilities:** Extracting common Tailwind patterns into a dedicated UI component library (like shadcn/ui).

## 7. Market Data: Yahoo Finance vs Premium Financial APIs

1. **Why it was selected:** Yahoo Finance (via open-source packages) provides free, reliable baseline quantitative data (Price, P/E, Market Cap).
2. **Why alternatives were not selected:** APIs like Bloomberg, FactSet, or even premium Alpha Vantage tiers cost hundreds or thousands of dollars and require complex onboarding.
3. **Benefits for this project:** Accessible immediately, completely free, and provides enough data to prove the AI concept.
4. **Trade-offs accepted:** Unofficial APIs can break if Yahoo changes their DOM/endpoints, and rate limits are unpredictable.
5. **Future upgrade possibilities:** Integrating an institutional API (like Alpaca or Polygon.io) for guaranteed uptime and real-time ticks.

## 8. News Data: NewsAPI / Tavily Search vs Paid News APIs

1. **Why it was selected:** NewsAPI and Tavily provide excellent, free-tier access to recent web articles and headlines.
2. **Why alternatives were not selected:** Enterprise news feeds (like Reuters or Bloomberg feeds) are heavily paywalled.
3. **Benefits for this project:** Allows the News Agent to ground its analysis in real-time events happening today.
4. **Trade-offs accepted:** Free tiers often limit the number of articles returned or only provide summaries instead of full article text.
5. **Future upgrade possibilities:** Implementing a custom web scraper to pull full SEC filings (10-K/10-Q) for deeper fundamental analysis.

## 9. Architecture: REST API vs GraphQL

1. **Why it was selected:** A standard REST API over HTTP is the simplest way to communicate between client and server.
2. **Why alternatives were not selected:** GraphQL is powerful for querying deeply nested relational data, but AlphaLens AI only needs one primary endpoint (`POST /analyze`).
3. **Benefits for this project:** Quick to implement in Express; easy to debug using standard browser network tabs or Postman.
4. **Trade-offs accepted:** Potential for over-fetching or under-fetching data (not a huge issue here since the payload is a single report).
5. **Future upgrade possibilities:** GraphQL could be introduced if the app evolves into a complex dashboard with customizable widgets.

## 10. Rendering: Client-side rendering (CSR) vs Server-side rendering (SSR)

1. **Why it was selected:** CSR via standard React allows the browser to handle all UI logic, keeping the server completely free to focus on LangGraph execution.
2. **Why alternatives were not selected:** SSR (via Next.js) is unnecessary because SEO is irrelevant for an internal, authenticated, or utility-driven financial tool. 
3. **Benefits for this project:** Decoupled architecture and highly interactive UI states (like the live terminal feed).
4. **Trade-offs accepted:** Slower initial page load time compared to pre-rendered HTML.
5. **Future upgrade possibilities:** Implementing SSR for the Report view so users can share links to reports that render instantly with rich metadata previews.

---

## Engineering Principles

To ensure the success of this 7-day sprint, all code and architectural decisions were governed by the following principles:

*   **Simplicity over complexity:** We do not over-engineer. If a feature does not directly contribute to proving the multi-agent AI concept, it is cut.
*   **Explainability over black-box AI:** Users must trust the output. The architecture forces agents to "show their work" via the real-time terminal UI.
*   **Evidence over speculation:** The system is explicitly prompted to base all synthesis strictly on the fetched API data.
*   **Modular architecture:** Agents are decoupled. If the News API breaks, the Financial Agent can still function.
*   **Honest failure instead of hallucination:** If data cannot be retrieved, the backend is programmed to throw an explicit error rather than allowing the LLM to invent a fake P/E ratio.
*   **Build for maintainability:** Code is heavily commented, folder structures are logically separated (routes, agents, services), and the logic is easy to trace for any engineer reviewing the project.
